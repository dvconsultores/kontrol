B.2 Contenedores y orquestación

  • frontend (kontrol-web): sirve la SPA; healthcheck /healthz.
  • backend (kontrol-api): API Uvicorn en el puerto 8000; aplica las migraciones automáticamente al arranque (alembic upgrade head); healthcheck /api/v1/health/live.
  • watchtower: actualización automática de imágenes etiquetadas, con reinicio rodante opcional.
  • Red: red bridge kontrol-net de nombre fijo para que el proxy de entrada pueda enrutar a kontrol-web:80 y kontrol-api:8000 sin exponer puertos.
  • Base de datos: externa (cada cliente la suya), alcanzada por el backend mediante KONTROL_DB_URL.

B.3 Sistema operativo soportado y servidor

  • Servidor: Linux (imágenes base Debian slim y Alpine); cualquier host con motor Docker compatible.
  • Cliente: navegadores web modernos de escritorio (Chrome/Edge, Firefox y Safari en sus versiones vigentes).
  • Navegadores compatibles: la SPA se compila para navegadores modernos con soporte ES2020+.

B.4 Esquema de comunicaciones

  • El navegador se comunica con el frontend servido por Nginx y con la API a través de /api/v1 mediante HTTPS.
  • El backend se comunica con PostgreSQL mediante el driver psycopg2 (conexión TLS habilitable por configuración del motor).
  • El backend mantiene comunicación saliente opcional con el servidor central de licencias (contrato REST v1) para la sincronización de la licencia y los entitlements por módulo.
  • Todo intercambio de datos con el exterior se realiza sobre HTTPS/TLS a través del reverse proxy.

D. Base de datos

D.1 Motor y versión

KONTROL utiliza PostgreSQL como motor relacional. La base de datos es externa por instalación (cada cliente dispone de la suya) y se conecta mediante KONTROL_DB_URL con un usuario restringido (no superusuario). El despliegue de referencia y el respaldo usan imágenes PostgreSQL modernas (referencia postgres:18-alpine); el driver es psycopg2 2.9.10 y el ORM SQLAlchemy 2.0.36.

D.2 Estructura general y modelo de almacenamiento

  • Esquema relacional normalizado, gestionado por migraciones Alembic (versionadas y reproducibles; head 0011_homologacion).
  • Identificadores UUID en las entidades; fechas con zona horaria (DateTime(timezone=True)).
  • Modelo de datos: Installation → Tenant → Company → Branch → Establishment → Warehouse → Location, con aislamiento por empresa (ADR-011).
  • Datos fiscales versionados: reglas tributarias con vigencia (TaxRuleVersion), fuentes legales con hash (LegalSource).
  • Los eventos de auditoría son de solo agregar (append-only) (audit_events).

D.3 Identificación, numeración y correlativos de documentos fiscales

  • Series de numeración fiscal (FiscalNumberSeries): por empresa y establecimiento, con tipo de documento, prefijo y número siguiente.
  • Asignación atómica: se usa control de concurrencia optimista (lock_version) para evitar duplicados o saltos no controlados en la asignación de correlativos.
  • Números de control (ControlNumberBatch / ControlNumber): lotes de imprenta autorizada, con rango y estado individual (AVAILABLE / RESERVED / USED / VOID / LOST / DAMAGED) y referencia al documento que los consume.
  • La emisión real de documentos y su numeración definitiva corresponden al núcleo fiscal (spec 007) y quedan sujetas al proceso de homologación de la versión fiscal correspondiente.

D.4 Conservación de datos, restricciones e integridad referencial

  • Integridad referencial: claves foráneas y restricciones de unicidad gestionadas por PostgreSQL.
  • Conservación: los documentos fiscales y los eventos de auditoría se conservan de forma persistente; no se eliminan registros fiscales por operación normal (ver Separador 04).
  • Trazabilidad: cada operación se vincula a tenant, empresa, usuario, sesión, request y fecha/hora mediante el registro de auditoría.
  • Protección frente a eliminación/modificación: la historia fiscal es de solo agregar a nivel de aplicación; los permisos de base de datos se restringen (usuario de aplicación sin privilegios de borrado administrativo sobre tablas fiscales en producción).
